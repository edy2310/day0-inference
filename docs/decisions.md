# Decision log

Each entry records a choice that the implementation specification did not dictate.
Format: context, decision, consequence.

## D-01: Repository root is the `day0/` project root

- **Context:** The specification lays out the tree under a top-level `day0/` directory.
- **Decision:** The git repository root is the project root. `pyproject.toml`, `README.md`,
  `day0/` (package), `suites/`, `examples/`, `scripts/`, `tests/`, and `docs/` live at the top
  level of the repository.
- **Consequence:** Paths in the specification map one-to-one to repository paths.

## D-02: Development environment

- **Context:** The specification requires Python 3.11+ and tests on 3.11 and 3.12.
- **Decision:** Local development uses a `.venv` created from Python 3.11. CI runs the matrix
  3.11 and 3.12.
- **Consequence:** `.venv/` is git-ignored. Ruff line length is 100.

## D-03: Relative paths resolve against the YAML file

- **Context:** The specification says suite paths resolve against the YAML file. It gives the
  example `output_dir: ../results` but does not say what that path is relative to.
- **Decision:** Both `quality.suites[].path` and `run.output_dir` resolve against the directory of
  the YAML file. The directory is stored in `Day0Config.base_dir`, which is excluded from every
  hash.
- **Consequence:** `examples/fake.yaml` writes to the repository-level `results/`. The same
  configuration in another directory keeps the same config hash.

## D-04: `gsm8k_200.jsonl` cannot be built in this environment

- **Context:** The specification requires 200 items sampled from the GSM8K test split. Hugging
  Face is not reachable from the build environment. The GitHub repositories that publish the split
  are outside the repository scope granted to the session, so they were not read.
- **Decision:** `scripts/build_suites.py` takes the official `test.jsonl` as an input file
  (`--gsm8k-jsonl`) and does not download it. No GSM8K items are invented or substituted.
- **Consequence:** `examples/llama31-8b-h100.yaml` fails `day0 validate` until the file is built.
  The real-run example is validated in tests with placeholder files in a temporary directory.

## D-05: Shared filler-text module

- **Context:** The perf workload, the fake suites, and the synthetic long-context suite all need
  deterministic filler text from a word list.
- **Decision:** The word list and generators live in `day0/corpus.py`. Each function takes an
  explicit `numpy.random.Generator`. The specification does not list this module, so it is
  recorded here.
- **Consequence:** The generated suites depend only on the seed and this list. Changing the list
  changes every generated suite, so its contents are treated as frozen.

## D-06: Pydantic mypy plugin

- **Context:** `mypy --strict` reports `Missing named argument` errors for model fields that use
  `Field(default, ...)`.
- **Decision:** Enable `pydantic.mypy` with `init_typed` and `init_forbid_extra`.
- **Consequence:** Type checking of configuration models is accurate. Nested default models use
  `default_factory=lambda: Model()` so that mypy infers the type.

## D-07: Strict configuration validation

- **Context:** The specification asks for `extra="forbid"` and for validation rules with clear
  messages.
- **Decision:** Every model forbids unknown keys. Cross-field rules are model validators.
  `reference.enabled: false` is rejected, because the reference always runs.
- **Consequence:** A typo in a YAML key fails with the key name in the message.

## D-08: Forced-answer logit is `max + margin`, not `base + 50`

- **Context:** The specification's echo rule adds `+50` to the logit of each forced token. The
  forced distributions then have numerically zero tail mass, so every candidate has KL ≈ 0 and the
  calibration table in §18.1 cannot be reached. A fixed `+10` bias also lost the argmax in tests
  against an unlucky base draw.
- **Decision:** The forced token's logit is set to the current maximum plus `FORCE_MARGIN = 2.0`,
  before the candidate's noise is added. Greedy output is then always the forced text in the
  reference, and candidate noise can still break it.
- **Consequence:** The fake model's distributions have real tail mass, so KL responds to noise.
  Deviations from §13.1 are isolated in `day0/fake/model.py`.

## D-09: BOS is never generated by the fake model

- **Context:** §13.1 masks ids 258–511 but does not mention BOS (256).
- **Decision:** BOS is masked like the unused ids.
- **Consequence:** Every generated token is a byte, so streamed chunks always carry text.

## D-10: Client types differ slightly from the specification

- **Context:** The specification types `CompletionResult.output_ids` as `list[int]`. When a server
  returns text tokens and no ids, the ids cannot be recovered without re-tokenizing, which §24 forbids.
- **Decision:** `output_ids` is `list[int] | None`. `StreamResult` gains `chunk_counts_exact`.
  `InferenceClient` gains an optional `capture_dir` for `--capture-fixtures`.
- **Consequence:** Callers handle the `None` case. Exact match then falls back to text equality,
  and first divergence is undefined for that candidate.

## D-11: Tolerant parsing

- **Context:** The specification asks for tolerant parsing, but the real server fixtures are not
  available in this environment (no GPU).
- **Decision:** Parsers accept both `token_id:<n>` keys and plain numeric keys. Malformed
  Prometheus lines are skipped. Missing `usage` or `choices` is an error, not a partial result.
- **Consequence:** Fixture-based tests under `tests/fixtures/vllm/` skip until real captures are
  committed.

## D-12: The fake backend passes `common_args`

- **Context:** §7.3 gives the fake launch command without `backend.common_args`, but
  `examples/fake.yaml` sets `common_args: ["--startup-delay-s", "0.5"]`.
- **Decision:** The fake command is `[python, -m, day0.fake.server, --host, …, --port, …,
  *common_args, *server.args]`.
- **Consequence:** The shared startup delay in the example takes effect.

## D-13: `--logprobs-mode raw_logprobs` is added when absent

- **Context:** §2.3 says day0 always passes `--logprobs-mode raw_logprobs` explicitly, but the
  command in §7.2 does not include it.
- **Decision:** The flag is appended to the vLLM command unless `common_args` or the server's `args`
  already set `--logprobs-mode`, in which case the user's value is used unchanged.
- **Consequence:** Quality metrics always see raw logprobs, and an explicit override is still
  possible.

## D-14: Backend structure

- **Context:** The specification gives `get_backend(kind, cfg)` without the run-level values that
  `vllm serve` needs (model id, length limit, seed, logprob limit).
- **Decision:** `get_backend(kind, cfg, context)` takes a `BackendContext`. The shared
  launch-and-wait logic lives in `ProcessBackend` in `backends/base.py`.
- **Consequence:** `backends/base.py` holds more than the ABC. There are no other new modules.

## D-15: Stopping a server

- **Context:** §7.2 requires SIGTERM to the process group, a 60 s grace period, SIGKILL, a cooldown,
  and a GPU-memory wait.
- **Decision:** Implemented as written. The GPU wait runs only when `nvidia-smi` is on `PATH`, and
  on timeout it logs a warning rather than failing the run. A server that does not become healthy
  is stopped before `BackendStartError` is raised.
- **Consequence:** No orphan keeps GPU memory after a failed start.

## D-16: "Paired" bootstrap means resampling items

- **Context:** §12.3 asks for a paired percentile bootstrap of per-item means. Each candidate is
  compared with the reference through a per-item metric, not through two independent samples.
- **Decision:** The bootstrap resamples per-prompt values with replacement. The unit is always the
  prompt, never a position or a token. Seeds are derived from `run.seed`, the config name, the
  metric, and the slice.
- **Consequence:** Intervals reflect prompt-to-prompt variability. Within-prompt correlation does
  not inflate the sample size.

## D-17: Missing data per metric and per slice

- **Context:** Prompts longer than `prefill_max_prompt_tokens` skip the teacher-forced path. A
  slice can therefore contain items with no prefill data at all.
- **Decision:** For each gated metric, a slice is judged only on the items that have data for
  that metric. A slice with zero such items is "not covered" for that metric. A slice with at
  least one but fewer than `min_prompts_per_slice` such items is `INSUFFICIENT_DATA`.
- **Consequence:** The flip rate is always judged on every gold item in a slice. Prefill metrics
  are judged only where they exist, and the card states the coverage.

## D-18: Generation logprobs fallback applies only to candidates

- **Context:** §10.2 allows a single retry without logprobs when a server rejects them, and marks
  `generation_logprobs_available = false`.
- **Decision:** The fallback applies only to candidate runs. The reference never falls back,
  because its top-k distributions are the baseline. Exact match then compares text when token ids
  are not returned.
- **Consequence:** A reference that cannot return top-k fails the run with exit code 2.

## D-19: Perf requests are identical across configurations

- **Context:** §11.1 says the perf prompts are tokenized once on the reference and reused, so every
  configuration does identical work.
- **Decision:** `build_workload` seeds one generator per concurrency level from
  `derive_seed(seed, "perf", level)`. The shared prefix uses its own seed. Warmup requests come
  first inside each level. The stored workload is loaded by every candidate and never rebuilt.
- **Consequence:** Adding or removing a level does not change the prompts of the other levels.

## D-20: Goodput and SLO on requests without TPOT

- **Context:** A request with one output token has no TPOT (§11.3).
- **Decision:** Such a request counts as meeting the TPOT bound for goodput. The SLO check at
  level granularity uses the p99 TPOT of requests that have one, and is `False` when none do.
- **Consequence:** A workload with one-token outputs cannot meet the SLO by accident.

## D-21: Environment capture stores a host hash only

- **Context:** The specification asks for a hostname hash in `env.json`, not the raw name.
- **Decision:** `hostname_hash` is the first twelve hex characters of SHA-256 of the host name.
  The git commit is stored in `run.json`, not in `env.json`.
- **Consequence:** `env.json` does not reveal the machine name, and each field is best effort.

## D-22: Vectorized, context-keyed fake model

- **Context:** A one-generator-per-position model needed about 18 µs per prompt position. A
  prompt-logprob pass over the demo suite then took about 10 s per candidate, and a per-position
  `default_rng` made the server block its event loop.
- **Decision:** The base logits and the candidate perturbation come from a counter-based
  SplitMix64 hash, mapped to normals with Box-Muller. The value depends only on the seeds and the
  3-token context, so one position gives the same logits alone or in a batch (unit-tested).
  Distributions for context-only positions (before the assistant marker, with no
  position-dependent noise) are computed once per distinct context per prompt.
- **Consequence:** The fake model's random streams differ from the first implementation. All
  outcomes in §18.1 were recalibrated against the new streams, and they hold.

## D-23: Faster health polling for the fake backend

- **Context:** §7.2 polls `/health` every 2 s. The fake server starts in well under a second, so the
  demo spent about 2 s per server on the first poll.
- **Decision:** `FakeBackend` polls every 0.25 s. `VLLMBackend` keeps the specified 2 s.
- **Consequence:** Nine server starts in the end-to-end test save about 15 s.

## D-24: `top_k_logprobs: 5` in the demo configuration

- **Context:** Prompt logprobs carry `k + 1` entries per position. With the demo's ~400k prompt
  positions, `k = 20` produced about 160 MB of JSON per candidate, which made the demo impractical.
- **Decision:** `examples/fake.yaml` uses `top_k_logprobs: 5` and says so in a comment. The real
  configuration keeps 20, and the unit tests cover the estimator at any k.
- **Consequence:** The demo's outcomes are the same, and its run time is lower.

## D-25: Connection-level retries on POST

- **Context:** A server that computes on its event loop for seconds lets uvicorn close idle
  keep-alive connections. The client then reused one and failed with an empty `ReadError`. Every
  request is deterministic (greedy, seeded), so repeating one that never produced a response is
  safe.
- **Decision:** `InferenceClient._post` retries `ReadError`, `RemoteProtocolError`, and `WriteError`
  up to three times, with a short back-off. Other HTTP errors are raised at once.
- **Consequence:** Real servers that close idle connections are handled the same way.

## D-26: Prompt logprobs are computed off the event loop

- **Context:** The server computed prompt logprobs synchronously in the request handler.
- **Decision:** The handler runs the computation with `asyncio.to_thread`, so other requests keep
  being served while a long prompt is scored.
- **Consequence:** Concurrency in the demo behaves as intended, and the failure described in D-25
  does not recur.

## D-27: No quality records means `INSUFFICIENT_DATA`

- **Context:** `--skip-quality` produces candidates with no quality records. An empty evaluation
  would otherwise reach `PASS`.
- **Decision:** A candidate with no quality records is `INSUFFICIENT_DATA`.
- **Consequence:** A perf-only run cannot be mistaken for a gated pass.

## D-28: `run.json` is final before the card is rendered; `check` reads the given reference

- **Context:** The first end-to-end run wrote `ended_utc` after rendering, so `day0 report` produced
  a different card from the same run directory. `check` also read the perf workload from its own
  run directory, which does not contain it.
- **Decision:** `run.json` is written in its final form before `render_run`. The candidate phase
  reads the workload from the reference directory it was given (the run's own `reference/` for
  `run`, and `--reference` for `check`).
- **Consequence:** `day0 report` reproduces `card.md` byte for byte, and `check` works against a
  stored reference, as §15.1 describes.

## D-29: Card and report layout

- **Context:** §17.1 fixes the sections. §17.2 says `card.json` holds the same content.
- **Decision:** `card.json` is the report data itself, unrounded. `card.md` is rendered from it.
  Each candidate also gets `candidates/<name>/summary.json` with its per-slice aggregates, gate
  result, and errors, as §15.2 lists. Intervals are shown as `[lo, hi]`.
- **Consequence:** Anything the card shows can be checked in `card.json`.

## D-30: `check` writes a check record, not a card

- **Context:** §15.1 says `check` runs one candidate and gates it. It does not ask for a card.
- **Decision:** `check` writes `candidates/<name>/check.json` with the gate result, and it exits 0
  for PASS, 1 for any other status, and 2 for errors. It does not render a card or the Pareto chart.
- **Consequence:** A CI gate stays fast and does not need the other configurations.

## D-31: Suite builder

- **Context:** §9.4 asks for three committed suites, with deterministic builds.
- **Decision:** `scripts/build_suites.py` builds `longctx_synth.jsonl` (100 items, about 5 MB) and
  `chat_open_100.jsonl` (100 original prompts, stored in the script). It builds
  `gsm8k_200.jsonl` only when given the official file with `--gsm8k-jsonl` (see D-04). Two builds
  produce byte-identical files, which was checked.
- **Consequence:** The suites are reproducible, and the 5 MB file is the largest committed artifact.

## D-32: Validation script not run

- **Context:** §16 asks for `scripts/validate_kl.py` and `docs/kl_validation.md`. The script needs
  `torch` and `transformers`, and downloads the model from Hugging Face, which is blocked here.
- **Decision:** The script is written as specified and is not run. `docs/kl_validation.md` is a
  placeholder that says so.
- **Consequence:** Nothing in the repository claims a measured estimator error.

## D-33: End-to-end test duration

- **Context:** §19.2 requires the end-to-end test to finish in under 90 s on a CI runner.
- **Decision:** The test is kept as specified. On this 4-vCPU sandbox it takes several minutes,
  because the fake server serializes full prompt logprobs for ~400k positions per candidate, and
  each candidate also runs a full prefill pass. The remaining time is in JSON transfer and parsing,
  which the specified response shape requires.
- **Consequence:** The 90 s target is not met here. To meet it, reduce the long-context bucket of
  the fake suite, or make the fake server return prompt logprobs only for the requested positions
  (a deviation from the vLLM response shape). Either change must be recorded here first.
